Docker: để không surprise khi run ứng dụng

đi vào Docker, để không surprise khi run ứng dụng kiểu:

á đĩ mẹ nó run được ở máy của em

thì bản chất vẫn là make the environment consistent cho mọi môi trường (máy tôi, máy anh, máy của mấy đứa kia).

Vậy vấn đề gốc, làm sao để đóng gói?

muốn đóng gói thì… đóng gói thôi :D như chơi lego vậy, phải có từng component riêng lẻ, ghép lại thành hình thù.

máy tôi run Ruby 3.0 thì máy anh run 3.0, máy tôi dùng Postgres 14 thì máy anh cũng vậy.

biến số lớn còn lại là?… hệ điều hành và các system dependencies. mỗi thằng dùng một môi trường khác nhau thì có thể tạo ra vô số lỗi bất ngờ.

giải quyết → đơn giản bằng… ép environment của application về cùng một chuẩn luôn :D với Linux container, Docker đóng gói Linux userspace và các dependencies vào image, còn kernel vẫn dùng chung với host Linux.

trên Linux thì container dùng chung kernel của host nên rất nhẹ. còn trên macOS, để chạy Linux container, Docker phải chạy thêm một Linux VM ở bên dưới, nên cũng là một lý do mà trên macOS run Docker nó thường nặng và lag hơn, trong khi trên Ubuntu cấu hình yếu hơn vẫn có thể mượt hơn hẳn.

nhưng cùng image không có nghĩa là mọi môi trường giống hệt nhau. CPU architecture, kernel, config, secrets và dữ liệu vẫn có thể khác. Docker chuẩn hoá được một phần lớn environment, không xoá hết biến số.

Vài cái file / concept quan trọng

vậy là có đủ gia vị cần thiết:

  • Dockerfile → file mô tả cần dùng component nào cho con lego này: base image nào, cài package gì, copy source code nào, chạy command gì.

  • Docker Compose → nhiều lego kết hợp thì cần một file compose.yaml để define cách chúng phối hợp với nhau: app, postgres, redis, network, volume, dependency… thì chính là nó. như 5 anh em siêu nhân lúc gặp boss cuối thì lại kết hợp làm 1 thực thể, lúc này phải biết thằng nào là tay, thằng nào là chân, thằng nào cần thằng nào chạy trước :D

    Compose thường define services, và mỗi service có thể dùng một image có sẵn hoặc tự build image từ Dockerfile.

  • volume → vùng lưu trữ nằm ngoài lifecycle của container, data được giữ nguyên kể cả container bị xoá rồi tạo lại, miễn là không xoá luôn volume.

  • image → sản phẩm được build từ Dockerfile, là một package đã chứa environment và application cần thiết để chạy. nó nằm trên disk và bản thân nó không chạy.

  • container → chỉ là một instance của image, có thể đang chạy hoặc đã dừng. khi run thì ngoài disk, nó bắt đầu ăn thêm RAM và CPU. trên Linux nó không cần một virtual machine riêng cho từng container; nó dùng chung kernel của host và isolate process/network/filesystem…

đơn giản là vậy :D

CI/CD: khỏi phải nhớ 15 bước mỗi lần release

CI/CD nghe thì fancy, nhưng thực ra rất đơn giản: run một chuỗi công việc tự động để khỏi phải làm bằng tay, từ đó giảm surprise.

manual process luôn có nhiều biến số:

  • hôm nay tôi nhớ chạy test, ngày mai tôi quên
  • thằng A deploy theo cách này, thằng B deploy theo cách khác
  • có người nhớ build production mode, có người quên
  • có người chạy migration trước, có người deploy trước rồi mới nhớ migration :D

CI/CD đơn giản là: có event xảy ra → chạy một procedure đã được define sẵn. ví dụ:

thay vì mỗi lần release lại có một người ngồi nhớ 15 bước, ta encode 15 bước đó vào một file.

Bitbucket thì bitbucket-pipelines.yml. GitHub thì GitHub Actions workflow. CircleCI, GitLab CI… cũng vậy. syntax khác nhau, provider khác nhau, nhưng cách làm vẫn giống nhau:

event X xảy ra → chạy command A → B → C

CI và CD

CI: code được tích hợp thường xuyên → check ngay xem có gì vỡ không. ví dụ build, lint, unit test, integration test, Playwright… mục tiêu là detect surprise càng sớm càng tốt.

CD: sau khi mọi thứ pass → package/deploy bằng cùng một procedure. Continuous Delivery thì giữ bản build sẵn sàng để release, có thể vẫn chờ người duyệt; Continuous Deployment thì tự deploy khi đủ điều kiện. mục tiêu là tránh surprise ở release.

nên CI/CD về bản chất là reduce human variance bằng automation.

CI/CD provider thực sự làm gì?

repo không tự nhiên có CPU để chạy test :D nó chỉ gửi một cái order cho CI/CD provider:

“tao cần Linux, Node 22, Docker, rồi chạy mấy command này”

repo cũng chỉ order được thứ mà cửa hàng có. provider support Linux thì dùng Linux. có ARM runner thì mới order chạy native trên ARM được. provider không có cái gì thì YAML có viết thần chú cũng đéo summon ra được :D

nên có thể tưởng tượng CI/CD provider như một cửa hàng xây dựng:

  • file cấu hình pipeline là đơn đặt hàng + hướng dẫn thi công
  • runner là chỗ thực sự chạy mấy command đó

có provider cho một isolated slot sạch sẽ, có nơi dùng shared infrastructure, nhưng shared infrastructure vẫn có thể cấp environment riêng cho từng job. có thể dùng VM, container, Kubernetes pod, bare metal… tuỳ implementation của provider.

nếu muốn tự quản môi trường chạy thì dùng self-hosted runner. lúc đó CI/CD provider chủ yếu làm control plane, còn cái máy thực sự chạy code là của mình.

Security

runner thực chất chỉ là một cái máy đang chạy code mà repository yêu cầu, nên chuyện security cũng bắt đầu từ mấy câu hỏi rất cơ bản:

  • code này chạy ở đâu?
  • chạy với quyền gì?
  • được access secret nào?
  • network access tới đâu?
  • sau khi chạy xong còn state gì lại không?

có thêm chi phí khởi tạo và dọn environment, nhưng giảm surprise giữa các job rất nhiều.

persistent runner thì có thể tiết kiệm chi phí khởi tạo và tận dụng cache tốt hơn, nhưng nếu isolation ngu thì job trước có thể để lại file, credential, process, cache độc… cho job sau. shared infrastructure không tự động có nghĩa là các job dùng chung state.

case ngu nhất:

persistent runner + untrusted PR + production credentials + quyền rộng

địt con đĩ mẹ, lúc đó pipeline không còn là automation nữa mà thành remote code execution service :D

Một điểm rất quan trọng: test environment và parallelism

Playwright là thằng điều khiển browser. nếu test dashboard thật sự cần login qua hệ thống thật thì browser phải gọi tới một backend nào đó.

có 3 cách chuẩn bị môi trường test:

  1. test against staging/dev environment có sẵn.

Vậy tại sao cần Fargate?

chủ yếu để reduce friction. ECS + EC2 chạy được phần lớn workload mà mình chạy trên ECS + Fargate, nhưng với EC2 mình còn phải care:

trade-off rất obvious:

  • EC2 = nhiều control hơn, nhiều trách nhiệm hơn
  • Fargate = ít control hơn, ít friction hơn

Fargate không mạnh hơn EC2. nó chỉ remove một tầng khỏi đầu mình.

Cuối cùng, mỗi thằng giảm một kiểu surprise

  • Docker → bớt chuyện “máy em chạy được”, chuẩn hoá environment của application.

  • CI/CD → bớt chuyện quên bước hoặc mỗi người release một kiểu, đưa quy trình vào automation.

  • Playwright → bớt chuyện deploy xong mới biết user không login được, kiểm tra những hành vi đã được viết thành test.

  • CDK → bớt chuyện không nhớ đã click gì trên Console, đưa infrastructure vào code để diff và review.

  • ECS → bớt chuyện task chết mà không ai bù lại, duy trì workload theo desired state. Fargate thì bớt phần host phải tự quản, còn autoscaling điều chỉnh task/capacity theo policy.

  • Observability → bớt chuyện hệ thống có vấn đề mà không biết vì sao, dùng logs, metrics và traces để lần ra nguyên nhân, rồi đặt cảnh báo phù hợp.

không có thằng nào bảo đảm hệ thống không bao giờ vỡ. config sai thì automation vẫn chạy cái sai đó rất đều :D

cái đáng lấy không phải là thêm một đống tên vào tech stack, mà là biết mình đang giảm biến số nào, còn biến số nào phải tự chịu trách nhiệm.
