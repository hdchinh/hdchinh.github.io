Auth / Identity — Mental Model

1. OAuth 2.0

OAuth 2.0 chuẩn hóa cách Client lấy access token để gọi Resource Server. Điểm chính là quyền được cấp và cách kiểm tra quyền đó, không phải token có format gì.

Authorization Server phát token; Resource Server kiểm tra token để biết request đại diện cho client/user nào và được làm gì. Token có thể là JWT hoặc chỉ là random opaque string. Bên dưới vẫn là database, API endpoints, expiry và permission checks, không có magic.

Server-to-server

client_id là định danh unique; client_secret là random secret đủ mạnh. Ở đây client xin quyền cho chính nó, không có user tham gia.

User-delegated flow

Code đi qua browser redirect, access token thì không. Code có thể chỉ là random string; Authorization Server lưu nó cùng user, client, scope, hạn dùng và trạng thái đã sử dụng để kiểm tra khi đổi token.

2. OpenID Connect

OAuth cho client quyền truy cập tài nguyên; OIDC cho app biết user đã đăng nhập là ai.

OIDC xây trên OAuth 2.0 và thêm ID Token, thường là JWT. Identity Provider xác thực user rồi phát ID Token cho app. App kiểm tra chữ ký, issuer, audience và hạn dùng trước khi tin danh tính trong token.

Từ danh tính đã xác minh, app có thể tạo local session riêng. Session đó không bắt buộc là JWT; random session ID lưu trong database cũng được.

3. Identity database

Identity có thể nằm tập trung, nhưng dữ liệu của từng app vẫn nằm ở app đó.

Khi user login lần đầu, app verify ID Token, lấy cặp iss + sub để tìm local user. Chưa có thì tạo user và session ngay lúc đó: JIT provisioning.

4. SCIM

OIDC giúp app nhận diện user khi họ login. SCIM giúp đồng bộ vòng đời user giữa Identity Provider và các app.

Khi user được tạo, cập nhật, disable hoặc xóa, Identity Provider cần báo thay đổi đó cho SaaS, không thể chờ user login lại. SCIM 2.0 chuẩn hóa API cho việc này:

Giá trị nằm ở contract chung, không phải một technology đặc biệt.

5. AWS Cognito User Pool

Cognito User Pool giữ user và xử lý login. Sau khi user đăng nhập, Cognito phát token cho app.

Cognito xác thực user và ký token. Backend dùng public key của Cognito để verify chữ ký, không cần gọi Cognito mỗi request.

Public keys nằm ở JWKS endpoint của Cognito. Backend lấy key tương ứng để verify JWT: chữ ký hợp lệ cho biết token do Cognito ký và nội dung chưa bị sửa.

Backend vẫn phải kiểm token còn hạn và đúng mục đích trước khi dùng thông tin trong đó để quyết định quyền truy cập. API dùng Access Token, không coi ID Token (dành cho app nhận diện user) là vé gọi API.

Đổi lại, nếu backend chỉ verify token tại chỗ, việc disable user hoặc thu hồi quyền ở Cognito có thể chưa có hiệu lực ngay với token đã phát.

6. Passkeys / WebAuthn

Passkey cho phép user chứng minh mình giữ private key, mà không gửi private key hay vân tay cho website.

Nền tảng là asymmetric cryptography. Ví dụ login Facebook bằng passkey trên macOS:

Register Passkey

Facebook tạo random challenge; frontend gọi WebAuthn API để browser làm việc với authenticator trên macOS. Authenticator tạo cặp key: private key ở lại passkey store / iCloud Keychain; public key đi về Facebook. Facebook lưu user_id, credential_id và public key để dùng lúc login.

Login

Facebook gửi challenge mới. Touch ID chỉ cho phép macOS dùng private key tại máy để ký challenge, không gửi dữ liệu vân tay cho Facebook. Facebook dùng public key đã lưu để verify chữ ký rồi tạo session.

challenge là random bytes khác nhau cho mỗi lần xác thực, để chữ ký cũ không dùng lại được.

Standards

Backend chọn Rails/Go/Postgres/Redis tùy ý, nhưng vẫn phải tuân theo WebAuthn verification rules.

Core conclusion

OAuth, OIDC, SCIM và WebAuthn không phải magic. Chúng là contract để các hệ thống khác nhau cùng hiểu cách cấp quyền, xác nhận danh tính, đồng bộ user và đăng nhập bằng passkey.

Bên dưới vẫn là programming, database, cryptography, API và các bước kiểm tra. Nhờ dùng chung standard, mỗi app không phải tự invent auth protocol.
