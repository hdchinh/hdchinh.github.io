D01Exam tasks: 1.1, 1.2

Choosing security telemetry before turning on every available log

Situation and requirements

You own monitoring for a payment API. Availability dashboards show successful requests, but security cannot determine who changed a role or downloaded settlement reports. The reports live in a dedicated S3 prefix; application logs currently contain full request bodies.

This is a fictional design exercise. You must detect unauthorized changes and sensitive reads, retain investigation evidence, and avoid collecting card data in logs. Storage and on-call capacity are limited.

Options and decision

Approach What it provides Decisive limitation
Availability metrics alone Error rates, latency, health A successful unauthorized read can look healthy.
Enable every log and alert on every error Broad collection Sensitive payload exposure, high volume, and an unusable alert queue.
Threat-driven telemetry with delivery checks Evidence and alerts tied to protected assets Requires explicit source selection and ownership.

Choose threat-driven telemetry. Start with questions responders must answer, then select sources and destinations. Keep availability monitoring, but do not mistake it for security monitoring.

Mental model and flow

A dashboard is a view of evidence, not evidence that nothing happened.

AssumeRole / policy change → CloudTrail management events
Settlement object read → selected S3 data events
API authentication failure → sanitized application log
Sources → controlled storage → detection → named responder

CloudWatch metrics describe rates and thresholds. CloudTrail records supported API activity. GuardDuty produces threat findings from its enabled analysis, not a complete application audit history.

Essential mechanics

Configure a multi-Region trail for required management events and explicit data-event selectors for the settlement bucket/prefix. Management events alone do not capture S3 object reads. Record application actor IDs and correlation IDs without credentials or full payment payloads.

Send durable audit evidence to a separately controlled archive. Set retention from investigation and legal requirements; keep shorter operational retention where appropriate. Readers of security logs can learn sensitive operational details, so log access needs its own authorization.

Give each detection an owner and a response condition. A role-policy change outside an approved deployment window deserves different handling from routine successful reads. A metric filter only processes matching log events; it does not understand whether a change was authorized.

Monitor the monitoring path: last delivery time, ingestion failures, agent health, and expected source coverage. A quiet dashboard can mean missing telemetry. Resource health checks establish endpoint availability, not log completeness or absence of compromise.

Validation and when the answer changes

In a non-production account, perform a benign policy change and read a test settlement object. Verify each reaches the intended archive and detection path. Confirm an ordinary operator cannot delete archived evidence or read redacted payloads.

Stop a test collector and check that a missing-source signal appears. If the requirement becomes forensic capture of all object activity, expand selectors and capacity deliberately rather than claiming the targeted collection already covers it.

Remember and AWS docs

  • Successful requests can still be unauthorized business activity.
  • Management events and data events answer different questions.
  • Log delivery health needs separate monitoring.
  • Collection without an owner and response path is not detection.

D02Exam tasks: 1.2, 5.2

Preserving an organization’s API audit trail outside workload accounts

Situation and requirements

You manage audit logging for an organization. Workload administrators can delete their local logging buckets. An investigation must survive compromise of one workload account and include API changes across Regions plus access to selected confidential objects.

This is a fictional design exercise. New accounts must join the baseline automatically. Investigators need read access, but workload administrators must not control archive retention or encryption keys.

Options and decision

Approach Useful property Fit here
CloudTrail Event history Recent regional management events without creating a trail Not long-term retention or object-level data-event collection.
Independent account trails and local buckets Per-account customization Inconsistent coverage and a compromised local deletion boundary.
Organization trail to a protected archive account Central administration and durable cross-account delivery Requires correct bucket/key policies and verification of coverage.

Choose a multi-Region organization trail and a dedicated archive bucket. Separate permission to operate workloads from permission to administer evidence.

Mental model and flow

Member account API request
  → CloudTrail event selection
  → CloudTrail delivery service
  → archive-account S3 bucket + KMS key
  → restricted investigator role

An organization trail distributes a logging configuration. It does not make every possible event type enabled or every archive object immutable.

Essential mechanics

Use Organizations integration and an authorized management or delegated administrator account to manage the organization trail. Member accounts cannot change that organization trail, but central administrators remain a privileged attack surface.

Select required management events and separately configure data events. S3 object reads are not included merely because management logging is enabled. Check opt-in Region/account behavior and actual delivery after enrollment.

The destination bucket policy must allow the CloudTrail service to deliver under the intended organization path, with appropriate source restrictions. For SSE-KMS, the key policy must permit the required CloudTrail operations. Investigator S3 read permission does not independently grant KMS decryption.

Enable log-file integrity validation and retain the digest chain. Validation can reveal modification or missing delivered files; it does not prevent deletion or prove an event was selected in the first place. Where mandated, use supported S3 Object Lock retention in addition to restricted delete permissions. Keep key lifecycle controls aligned with evidence retention: retained ciphertext without a usable key is not readable evidence.

Validation and when the answer changes

Create a test account, perform management activity in two approved Regions, and read a selected test object. Confirm account IDs, Regions, event types, and delivery paths in the archive. Test workload-admin deletion denial and investigator read/decrypt access separately.

Alert on stopped logging, delivery errors, and unexpected gaps. If regional residency prohibits one archive location, retain controlled regional destinations instead of centralizing across a prohibited boundary.

Remember and AWS docs

  • Organization scope does not mean all event types are selected.
  • Delivery, investigation, deletion, and key administration are separate permissions.
  • Integrity validation detects problems; retention controls prevent certain changes.
  • Central logging still needs coverage and delivery checks.

D03Exam tasks: 1.2, 3.3

Selecting network evidence for a suspected outbound data transfer

Situation and requirements

You investigate unusual traffic from an application subnet. Exercise inputs show a large accepted outbound flow through a central egress network and a DNS query for an unfamiliar domain. No packet archive exists.

This is a fictional investigation exercise. You must establish what the evidence supports, locate the originating workload, and improve collection without claiming that network bytes prove specific customer records were stolen.

Options and decision

Evidence What it can establish What it cannot establish alone
VPC/TGW flow records Network endpoints, traffic counters and path context Application payload or business authorization.
Resolver query logs Observed DNS requests and answers Every connection or every repeated cached lookup.
Application/access and API logs Requests, actors and object operations when recorded Traffic outside the covered service/path.

Correlate the sources, starting from the workload and time window. Do not select one log type as a universal network audit trail.

Mental model and flow

Workload ENI → TGW attachment → egress/NAT → remote address
      │              │
 VPC flow logs   TGW flow logs
      └→ Resolver queries + application/API evidence

A NAT address is a translation point, not necessarily the originating application. Preserve identifiers needed to follow the path before and after translation.

Essential mechanics

VPC Flow Logs aggregate supported traffic metadata for network interfaces. Choose fields that retain source/destination, protocol, ports, timestamps, action, interface, and relevant packet-level address context. An ACCEPT record describes permitted network traffic at that observation point, not a successful login or completed data transfer.

TGW flow logs add visibility at the transit gateway, useful when traffic crosses accounts or routing domains. They do not replace workload ENI or application context. Flow logs are not packet captures, have collection limitations, and are not guaranteed to account for every packet.

Resolver query logging records eligible queries through Route 53 Resolver. Caching and alternative DNS paths create limits. A lookup does not prove a subsequent connection; a connection to an IP need not create a fresh DNS query.

Resolve the ENI to its workload at the event time, not only its current owner. Compare flow intervals, DNS answers, and application request IDs. If S3 is involved, selected CloudTrail data events can identify object operations, but enabling them now does not recreate missing historical events.

Validation and when the answer changes

Generate a benign request from a test workload through the same path. Confirm which identifiers and timestamps can be correlated and which remain ambiguous. Record source gaps and clock differences explicitly.

If payload-level proof is legally required, design approved prospective capture or application auditing with privacy controls. Do not manufacture that proof from byte counters.

Remember and AWS docs

  • Accepted traffic is not evidence of authorized business use.
  • DNS lookup, connection, and object read are distinct observations.
  • Translation and ephemeral workloads complicate attribution.
  • Missing historical telemetry cannot be generated retroactively.

AWS: VPC Flow Logs · AWS: Resolver query logs

D04Exam tasks: 1.1, 1.2

Giving a central operations team visibility without unrestricted workload access

Situation and requirements

You support applications running across several accounts in one Region. On-call engineers need logs and metrics, but currently assume administrator roles just to diagnose errors. Workload teams own operational retention; audit evidence already has a separate archive.

This is a fictional design exercise. Central troubleshooting must not grant deployment access or silently duplicate every log into another account.

Options and decision

Approach Mechanism Fit here
Read-only roles in every source account Operators switch account contexts Valid, but fragments investigation and role maintenance.
CloudWatch cross-account observability Monitoring account views selected source telemetry Matches the same-Region operational requirement without copying logs.
Central log replication An independent destination stores another copy Appropriate for separate retention/control, which this operational use case does not require.

Choose cross-account observability with narrowly selected telemetry. Keep the audit archive as a separate control rather than pretending a shared view is an independent copy.

Mental model and flow

EC2 agent / Lambda / API Gateway → source-account log groups
Source-account OAM link → monitoring-account OAM sink
Authorized monitoring user → shared telemetry queries

The sink accepts links; the source link specifies what is shared. This does not grant the monitoring team arbitrary access to compute or application data.

Essential mechanics

Configure a monitoring-account sink policy to accept intended source accounts or organization members. Create source links for the required telemetry types and filters. CloudWatch cross-account observability operates within a Region; build the relationship in each required Region rather than assuming one link is global.

Sharing does not start collection. EC2 requires an appropriately configured agent for selected guest logs. Lambda requires execution-role logging permissions and its supported logging configuration. API Gateway needs stage-specific access/execution logging as applicable to its API type. These are different producers even if their destination is CloudWatch Logs.

Give monitoring users query/read permissions, not source-account administration. Shared log content may contain tenant or operational information, so limit which log groups are exposed and sanitize at the producer.

Retention and encryption remain properties of the source storage. If a source log group is deleted or retention expires, a link cannot recover those records. A compliance requirement that evidence survive source-account compromise therefore calls for protected copying/archiving, not OAM alone.

Validation and when the answer changes

Generate one test event from each producer and query it from the monitoring account. Verify unrelated log groups are not shared and the operator cannot modify the source workload. Test a missing-link versus missing-producer case separately.

Choose a supported centralization pipeline when independent retention, cross-Region storage, or an external SIEM requires actual delivery of another copy.

Remember and AWS docs

  • A shared view is not a backup or immutable archive.
  • Sink policy and source link jointly establish sharing.
  • Producer configuration still determines whether logs exist.
  • Operational read access does not require workload administration.

D05Exam tasks: 1.1, 6.1

Finding accounts and workloads missing threat detection coverage

Situation and requirements

You own organization-wide threat detection. The central console shows GuardDuty findings, but an exercise inventory identifies an unmonitored EKS cluster in a secondary Region. Management assumes that enabling the service once covered every workload.

This is a fictional investigation exercise. You must identify actual gaps across account, Region, and protection plan without treating an empty finding list as a clean bill of health.

Options and decision

Check What it proves Missing information
Count aggregated findings Some findings reached the administrator Silent or unprotected resources remain invisible.
Check account-level enablement Basic service configuration exists Optional protections and runtime prerequisites can still be missing.
Reconcile inventory with protection coverage Expected resources are matched to enabled, healthy analysis Requires service-specific status checks and ownership.

Choose inventory-to-coverage reconciliation, then route findings centrally. Aggregation is useful only after confirming sources are protected.

Mental model and flow

Organization accounts × approved Regions × workload inventory
  → required protection plans
  → enabled status + runtime coverage health
  → exceptions and remediation owners

A detector answers security questions only for the data sources and workloads it actually analyzes.

Essential mechanics

GuardDuty is regional. Configure the delegated administrator and organization settings in each operating Region, including treatment of existing and future members. Review each relevant protection plan rather than relying on a single enabled flag.

Runtime Monitoring involves supported workload types and working collection components. For EKS, examine coverage and agent health, not merely cluster existence. Account-level settings cannot prove that a runtime agent is operating correctly on every eligible resource.

GuardDuty independently consumes supported foundational data sources; enabling customer-facing CloudTrail or flow-log delivery is not generally a prerequisite for that analysis. However, your investigation archive still needs its own logging configuration. GuardDuty findings are not a substitute for retained raw evidence.

Schedule checks against the workload inventory and distinguish unsupported resources, intentionally excluded resources, and failed deployment. Assign an exception owner and expiry rather than silently classifying every unsupported item as protected.

Inspector identifies supported vulnerability exposures; configuration assessments identify control drift. Neither replaces GuardDuty threat analysis. A critical package vulnerability and a suspicious process are different observations even when they affect the same host.

Validation and when the answer changes

Enroll a test account and workload in two intended Regions. Verify the required protections and coverage states, then check finding routing with supported sample findings. Sample delivery proves the route, not detection of a real attack.

If a workload type is unsupported, document the gap and choose appropriate host/application telemetry. Do not mark coverage complete merely because its account appears in the administrator console.

Remember and AWS docs

  • No findings can mean no detection coverage.
  • Account enablement, protection plans, and runtime health are separate checks.
  • Aggregation does not enable missing sources.
  • Threat, vulnerability, and configuration signals answer different questions.

AWS: GuardDuty Organizations management · AWS: Runtime Monitoring

D06Exam tasks: 1.1, 1.2

Prioritizing correlated security findings instead of counting alerts

Situation and requirements

You lead a small security operations team. Exercise inputs include an internet-reachable EC2 instance, a critical vulnerable package on it, and suspicious activity involving its role. Another account has hundreds of low-impact configuration findings.

This is a fictional prioritization exercise. You must direct responders to the most consequential risk without declaring a compromise solely from a score.

Options and decision

Approach Benefit Limitation
Sort all findings by severity Simple queue Ignores exposure, asset value, and relationships between signals.
Correlate resource, identity, exposure and threat context Builds a defensible investigation priority Depends on source coverage and accurate resource relationships.
Investigate every raw event first Detailed evidence Too slow as the initial triage method.

Prioritize the correlated exposure and threat case, then investigate supporting evidence. Keep the configuration backlog visible, but do not equate finding count with current risk.

Mental model and flow

CSPM posture + Inspector vulnerability + GuardDuty threat
  → resource/identity correlation in Security Hub
  → prioritized investigation
  → raw evidence and scoped response

A finding is a producer’s security observation. Several findings may describe one risk; one finding may still require substantial validation.

Essential mechanics

The supplied SRA distinguishes Security Hub CSPM, formerly called Security Hub, from the broader Security Hub experience. CSPM evaluates posture controls and ingests findings. Its controls often depend on AWS Config recording the relevant resources. Central configuration manages enabled standards/controls; cross-Region aggregation collects findings. Those are different operations.

Security Hub correlates and enriches supported security signals into exposure and threat context. This helps prioritize a vulnerable, reachable resource over an isolated vulnerability with no relevant exposure. It does not prove an attacker successfully used that path.

Retain finding identifiers, source product, resource ARN, account, Region, timestamps, and workflow state. A stale finding from a replaced instance must not silently become evidence about its replacement. Verify coverage and freshness before treating correlation as complete.

Suppressing a known exception changes handling, not the underlying configuration. Resolving a ticket does not patch a package. Separate triage status, provider-reported finding state, and actual remediation evidence. Bound automated workflow changes by owner and expiry.

Validation and when the answer changes

Trace each exercise signal to its original resource and producer. Verify the instance is still exposed and the package version still affected. Review role/API evidence before claiming credential misuse.

Test that a controlled source finding reaches the administrator and retains its identifiers. If investigation requires request-level chronology, query the retained logs; a finding aggregator is not the complete raw-event archive. If the correlated source is absent, document reduced confidence rather than inventing the missing signal.

Remember and AWS docs

  • Severity is an input, not the entire risk decision.
  • Posture checking, aggregation, and correlation have different jobs.
  • Workflow status is not proof of remediation.
  • Correlated exposure still requires incident validation.

D07Exam tasks: 1.2, 3.1

Integrating AWS and third-party telemetry into a security data lake

Situation and requirements

You manage a SOC that uses an external SIEM. AWS network/API events and a vendor’s edge-security events have incompatible schemas. Analysts need repeatable queries, while a contracted partner should see only approved sources.

This is a fictional design exercise. Data must remain in approved Regions, and the vendor integration cannot receive unrestricted access to every security log.

Options and decision

Approach Mechanism Trade-off
Independent SIEM connector for every source Transform and deliver separately Fast for a small estate, but duplicates schema and access-management work.
Security Lake with supported and custom sources Standardized security data in your account Custom producers must satisfy schema and ingestion requirements.
Dump arbitrary JSON into a bucket Cheap initial storage No assured query compatibility, cataloging, or controlled subscription model.

Choose Security Lake with explicitly scoped ingestion and subscribers. Keep the SIEM responsible for its detections and workflows; the lake is not itself a replacement detector.

Mental model and flow

Supported AWS source ───────────────┐
Vendor events → OCSF transformation ├→ regional Security Lake
                                   └→ approved subscriber → SIEM

OCSF is a common security-event schema. Normalization makes comparable fields queryable; it does not make different event sources equally complete or trustworthy.

Essential mechanics

Enable supported AWS sources in the intended accounts and Regions. Security Lake normalizes supported sources to OCSF and stores data in an analytics-friendly format. Custom sources must deliver records meeting the required OCSF, format, and ingestion contract; placing raw vendor JSON alongside the data is not equivalent integration.

Preserve actor, resource, source-product, event-time, and original identifier semantics during transformation. Do not map an edge client IP to an AWS principal or replace event time with ingestion time. Version the mapping when the vendor schema changes.

Select subscriber access according to how the consumer reads data. Data-access subscribers and query-access subscribers have different permissions and integration paths; query access uses the supported catalog/Lake Formation model. Scope sources, accounts, and Regions instead of handing the vendor broad bucket access.

Configure retention and any regional rollup deliberately. A rollup copies data across a boundary and may violate residency requirements. Encryption, subscriber roles, delivery notifications, and subscriber processing failures all need monitoring.

Validation and when the answer changes

Send one benign native event and one vendor event with known identifiers. Query both and verify timestamps, actor fields, schema validity, and source attribution. Confirm the partner cannot read a non-subscribed source.

Pause the vendor producer and confirm missing-data detection. If the SIEM already satisfies normalization, retention, and access needs at smaller scale, direct connectors may be simpler. Do not add a lake merely because it appears on an architecture diagram.

Remember and AWS docs

  • Normalization is not threat detection.
  • Custom sources must meet a real ingestion contract.
  • Subscriber permissions should match the intended data subset.
  • Regional rollup is a data-residency decision.

D08Exam tasks: 1.2, 2.2

Reconstructing an actor’s timeline across mismatched log sources

Situation and requirements

You investigate an assumed-role session suspected of downloading reports. Exercise inputs include CloudTrail records in S3, application JSON in CloudWatch Logs, and flow records in S3. Their clocks, identifiers, and field names differ.

This is a fictional investigation exercise. You need a reproducible timeline without first migrating all telemetry into a new platform.

Options and decision

Approach Strength Constraint
Query existing stores with Logs Insights and Athena Fast investigation using retained evidence You must reconcile schemas and identifiers deliberately.
Ingest into OpenSearch Indexed search and ongoing correlation Adds ingestion, mapping, access-control, and operational work.
Use an existing CloudTrail Lake event data store SQL over its retained events It does not contain arbitrary historical logs unless ingested.

Query the existing stores first. Use Logs Insights for application evidence and Athena for cataloged S3 records. Build an explicit correlation table rather than assuming a dashboard joins everything correctly.

Mental model and flow

CloudTrail session + event time → candidate API operations
Application actor + request ID → candidate business requests
ENI + interval + destination → supporting network observations
                → evidence-linked timeline

Correlation is a reasoned association, not proof that two similar timestamps describe the same action.

Essential mechanics

Keep original records and separately derive normalized fields such as UTC event time, account, session principal, request identifier, and resource. Distinguish event time from ingestion time. Record timezone assumptions and uncertainty where sources lack precision.

A role ARN identifies a role, not a unique session. Use available session context, principal identifiers, access-key identifiers, and request IDs appropriately; never log secret credential material. Map ephemeral ENIs and resource ownership at the event time.

Athena needs correctly parsed/cataloged S3 data and appropriate S3, catalog, and encryption permissions. Partition pruning limits scanned data. Logs Insights can extract fields and summarize application events, but a missing application actor cannot be reconstructed from an IP alone.

OpenSearch is useful when repeated low-latency searches justify ingestion and indexing. Managed Grafana visualizes data from authorized sources; it is not the raw archive or a substitute for source permissions.

Lifecycle boundary: AWS states CloudTrail Lake is closed to new customers starting May 31, 2026. An existing customer’s retained event store may remain relevant, but it is not the default recommendation for a new deployment.

Validation and when the answer changes

Use a benign known request to test joins and timestamp conversion. Include a deliberate same-role, different-session counterexample. Preserve query text, source scope, and evidence references so another analyst can reproduce the result.

For ongoing high-volume correlation, evaluate a dedicated indexing or SIEM pipeline. Label gaps as unknowns rather than reporting unobserved access as impossible.

Remember and AWS docs

  • Event time and arrival time are different.
  • A shared role or IP is not a unique actor.
  • Visualization cannot recover missing source evidence.
  • Choose tools around retained data and supported availability.

D09Exam tasks: 1.1, 1.3

Diagnosing a security event that never reaches the on-call team

Situation and requirements

You receive a report that a GuardDuty test finding never paged anyone. Exercise inputs show the finding in the expected Region, a matching EventBridge rule invocation, and failed target delivery. The target is an encrypted SNS topic.

This is a fictional troubleshooting exercise. Restore the alert path without making the topic public, disabling encryption, or repeatedly generating noisy findings.

Options and decision

Response Effect Fit
Change the finding rule immediately Might change event matching Evidence already shows an invocation; start farther downstream.
Grant broad access or remove encryption May hide the failure Removes intended security boundaries and obscures the cause.
Trace each hop and repair the failing permission Preserves the intended design Requires separating topic, key, and subscriber failures.

Inspect SNS target delivery and its authorization path first. The supplied evidence narrows the failure but does not yet prove whether SNS or KMS authorization is responsible.

Mental model and flow

GuardDuty finding → EventBridge match → target delivery
  → SNS authorization + encryption → confirmed subscription → responder

Seeing the event at one stage proves only that stage succeeded.

Essential mechanics

Confirm account, Region, event pattern, and target ARN. Use invocation/failure metrics and a configured dead-letter destination where supported to locate failed delivery. A matching event does not guarantee the target accepted it.

An SNS resource policy must allow the intended publisher under appropriate supported source conditions. For an encrypted topic, the customer-managed key policy must also allow required service use. Topic permission and KMS permission are distinct checks; granting the operator access does not automatically authorize the publishing service.

After SNS accepts the message, inspect subscription confirmation, filter policies, endpoint status, and downstream delivery. A subscriber filter can intentionally discard a valid publication.

A CloudWatch alarm route has additional stages: the metric/filter must produce the expected datapoint, the alarm must evaluate its configured periods and missing-data behavior, and an action must occur on the relevant state transition. A log event does not guarantee a new alarm transition.

AWS User Notifications is another managed notification route for supported events, not a repair for missing producer evidence. Whichever route is used, assign delivery health and escalation ownership.

Validation and when the answer changes

Replay a controlled representative event after the narrow policy fix. Confirm target success and actual subscriber receipt, then verify an unrelated publisher is denied. Do not stop at an invocation counter.

If no rule invocation existed, return to source delivery and pattern matching. If SNS accepted the message, investigate the subscriber instead of broadening the KMS policy again.

Remember and AWS docs

  • Event visibility, target acceptance, and human receipt are separate milestones.
  • Resource and KMS policies can fail independently.
  • Alarm state changes differ from individual log events.
