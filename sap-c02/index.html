N01Exam tasks: 1.1, 1.4

Connecting product teams without opening development access to production

Situation and requirements

You are the platform architect at a retailer. Checkout, inventory, and fulfillment teams run applications in 20 VPCs, isolated AWS networks, across several accounts. Your network team currently adds individual peering connections whenever applications need to communicate. As new projects join, reviewing those connections and routes is becoming difficult.

Problem: A growing network with connection-by-connection management.
Need: Communication within dev and within prod; both need the shared package repository and monitoring services.
Must prevent: Dev-to-prod access in either direction, including through shared services.
Key constraint: General IP connectivity, not just one API. All VPCs are in one Region with non-overlapping address ranges (CIDRs).

This is a fictional design exercise.

Options and decision

Option Mental model Fit for this problem
VPC peering A direct connection between two networks Works, but each communicating pair needs its own connection and routes. A shared VPC cannot act as a transit hub through peering.
PrivateLink A private entry point to one published service Suitable for exposing the repository alone, not the required general connectivity between applications.
Transit Gateway (TGW) A routing hub with separate routing domains Centralizes connectivity while separate route tables isolate environments. Adds attachment and data-processing charges.

Choose TGW with separate dev, prod, and shared-services route tables. This replaces the growing set of pairwise connections with a standard attachment process. Isolation still depends on configuring the routes correctly.

Mental model and flow

TGW is a central router, not one unrestricted network. An attachment connects a VPC to it; the source attachment determines which routing table handles an incoming packet.

A development build agent downloading a package follows:

Build agent
  → VPC route table
  → dev VPC attachment
  → TGW dev route table
  → shared-services attachment
  → package repository

The response enters through the shared attachment and uses the TGW shared route table to return to dev. A dev packet addressed to prod finds no permitted route in the dev table and is dropped.

Essential mechanics

The networking account owns the TGW and shares it through AWS Resource Access Manager (RAM). Application accounts attach their VPCs.

  • Association selects the TGW route table used by traffic arriving from an attachment.
  • Propagation adds an attachment’s routes to selected TGW route tables. It does not determine which table that attachment uses for incoming traffic.

Configure those independently:

Source attachment Associated table Routes in that table
Dev Dev Dev VPCs and shared services
Prod Prod Prod VPCs and shared services
Shared services Shared Dev and prod VPCs for return traffic

Workload subnet route tables must also send approved remote destinations to TGW. Avoid default associations, propagation, or broad routes that accidentally connect dev and prod.

The shared table permits routing to both environments, not only responses. Routing is not a one-way access policy. Restrict ports and sources with security groups, authenticate service requests, and do not let shared hosts proxy traffic between environments.

Validation and when the answer changes

Before rollout, verify:

  • Dev and prod can use the repository and monitoring services, including return traffic.
  • Production checkout can reach production inventory, while dev-to-prod and prod-to-dev connections fail.
  • A newly attached VPC receives only its intended routes, not unrestricted default propagation.

If access is unexpected, inspect both VPC and TGW routes. Passing these checks does not prove a compromised shared host cannot bridge environments.

Change the requirements, change the choice: two VPCs with one stable relationship favor peering; consumers needing only a provider API favor PrivateLink. Overlapping CIDRs require an address-management or service-exposure solution, not merely adding TGW.

Remember and AWS docs

  • Peering is non-transitive: A↔B and B↔C do not give A↔C connectivity.
  • TGW centralizes routing; separate route tables define network reachability boundaries.
  • Association selects the lookup table; propagation supplies routes to tables.
  • RAM shares access to the TGW across accounts, not application permissions.
  • Shared-service connectivity needs both return routes and controls against unintended access.

N02Exam tasks: 1.1, 4.2

Integrating an acquired company’s pricing API when both networks use the same IP range

Situation and requirements

You are the cloud architect at a distributor that has acquired a supplier. Your order application must retrieve the supplier’s prices before the next sales cycle. Both companies use 10.0.0.0/16 in separate AWS accounts in the same Region, so an address could identify a host in either network.

The supplier can publish its existing HTTPS API but cannot renumber production this month. You need private access to that API, not its databases or entire network. The supplier does not need to initiate connections into your VPC.

This is a fictional design exercise.

Options and decision

Option Mechanism Fit here
Peering or ordinary TGW routing Connect the networks by destination address Peering rejects overlapping CIDRs; TGW does not translate conflicting addresses.
Renumber or build a translated network Introduce unique addresses and adjust routing/DNS Supports broader integration, but adds migration or translation work for one API.
PrivateLink Publish one service through private endpoints Meets the narrow requirement without merging address spaces; adds endpoint and load-balancer costs.

Choose PrivateLink. The application connects to an address inside its own VPC, while AWS carries the request to the supplier’s published service.

Mental model and flow

PrivateLink is a private service entrance, not a bridge between two networks.

Order service → consumer endpoint ENI → PrivateLink → supplier NLB → pricing API

An ENI is a network interface. The endpoint’s ENIs use addresses from the consumer’s subnets, avoiding a route to the conflicting supplier CIDR. Responses return over the established connection; the provider cannot use this service to initiate arbitrary connections back.

Essential mechanics

The supplier places the API behind a Network Load Balancer (NLB), creates an endpoint service, allows your account, and accepts its endpoint connection request. Your account creates an interface endpoint and limits its security group to HTTPS from the order application.

Configure a stable DNS name and matching TLS certificate. A verified private DNS name on the endpoint service can preserve the API hostname. An NLB TCP listener can pass TLS through to the API targets. Permission to establish an endpoint is not permission to retrieve customer prices: the API still authenticates and authorizes each caller.

Use endpoints and healthy provider capacity across multiple supported Availability Zones. Compare AZ IDs across accounts, since AZ names can map differently. Redundant endpoints cannot compensate for a single unhealthy API backend.

Validation and when the answer changes

  • Resolve the API name from the consumer VPC and make an authenticated call without internet egress.
  • Verify an unapproved account cannot establish an accepted connection, and an unauthenticated application cannot retrieve prices.
  • Confirm arbitrary supplier hosts remain unreachable; exercise loss of provider targets in one AZ.

If the acquisition later requires directory integration or general bidirectional connectivity, revisit renumbering or address translation. PrivateLink solves the current service boundary, not the companies’ long-term network consolidation.

Remember and AWS docs

  • Overlapping CIDRs make ordinary network routing ambiguous.
  • Interface endpoints expose private addresses in the consumer VPC.
  • PrivateLink exposes a service, not the provider’s entire network.
  • Connection approval, API authorization, and TLS solve different problems.
  • Availability requires healthy capacity on both sides of the endpoint.

N03Exam tasks: 1.1, 1.3, 4.2

Keeping a hybrid order platform operational when a Direct Connect location fails

Situation and requirements

You manage networking for a distributor whose AWS order platform still depends on an inventory system in its data center. During shipping hours, API calls and replication together require 2 Gbps. Operations needs that capacity after losing either a circuit or an entire Direct Connect location.

The application’s retries can tolerate a short failover interruption, not prolonged congestion. The site’s internet connection offers less than 500 Mbps for emergency use. Sensitive traffic must remain encrypted end to end; the existing applications support TLS.

This is a fictional exercise; capacities are assumed requirements, not benchmarks.

Options and decision

Option What it provides Why it fits or loses
Direct Connect plus internet VPN An independent fallback path The internet link cannot carry the required load. Suitable only for degraded operation.
Several DX circuits at one location Some circuit and equipment redundancy All paths can disappear with the same location.
DX paths at two locations Location diversity and dedicated capacity Meets the requirement if surviving paths, routers, and carrier links carry the full workload. Costs more.

Choose diverse DX paths at two locations. One adequately sized connection per location covers the stated single-failure cases. Two per location add local device redundancy and maintenance flexibility, following AWS’s maximum-resiliency topology; that extra cost needs justification.

Mental model and flow

Redundancy means enough independent capacity remains after failure, not just that another cable exists. A DX location is a connectivity facility, not an application Availability Zone.

Data-center router → DX transit virtual interface → Direct Connect Gateway → Transit Gateway → application VPC

Both locations provide this logical path. The Direct Connect Gateway connects DX to the regional TGW; it does not encrypt traffic.

Essential mechanics

Use separate customer routers and diverse carrier paths. Two circuits sharing a conduit can fail together. Size the surviving path above 2 Gbps with headroom, checking every link and device rather than only the AWS port rate.

BGP advertises reachable network prefixes and selects paths. Verify failover in both directions: stateful firewalls may reject traffic when requests and responses follow incompatible paths.

DX is not encrypted by default. Enforce TLS for application and replication sessions. If IP-layer encryption becomes mandatory, assess supported VPN-over-DX options and their throughput separately. MACsec protects a supported link segment, not automatically the whole application path.

Keep internet VPN as a last resort. Explicitly pause bulk transfers in that mode so essential operations do not compete with 2 Gbps of normal demand on a sub-500-Mbps link.

Validation and when the answer changes

  • Under representative load, remove a circuit, a router, and one location in separate exercises.
  • Measure convergence, failed requests, retry recovery, and surviving-path utilization. Verify retries cannot create duplicate orders.
  • Exercise internet-only operation and confirm both traffic reduction and encryption.

A healthy BGP session does not prove usable application capacity. If the business also requires survival of a data-center outage, add a compute/data recovery design; diverse DX connections cannot replace the unavailable inventory system.

Remember and AWS docs

  • Location diversity addresses failures that same-location circuits cannot.
  • Backup paths need sufficient end-to-end capacity.
  • BGP recovery can interrupt existing sessions.
  • Private connectivity and encryption are separate requirements.
  • A low-capacity VPN is a degraded fallback, not a full-service substitute.

N04Exam tasks: 1.1, 4.2

Making private application names resolve during a phased migration to AWS

Situation and requirements

You are migrating a manufacturer’s order application to AWS while its ERP system remains at the factory. The VPN works and private addresses are reachable, but office users cannot resolve orders.cloud.example.com; the new application cannot resolve erp.corp.example.com.

The infrastructure team must retain ownership of corporate DNS, and the cloud team owns its private application records. You need stable hostnames in both directions without publishing internal records or maintaining hosts files.

This is a fictional design exercise using example.com names.

Options and decision

Option Mechanism Fit here
Hosts files Copy service addresses to clients Breaks when addresses change and creates manual update work.
EC2 DNS forwarders Operate servers that relay queries Valid for custom DNS behavior, but adds patching, capacity, and availability duties.
Route 53 Resolver endpoints Managed forwarding by domain suffix Preserves namespace ownership with less server management; endpoint charges still apply.

Choose Resolver inbound and outbound endpoints with conditional forwarding. The VPN supplies transport; Resolver supplies the missing DNS integration.

Mental model and flow

Inbound and outbound describe the direction of a DNS query relative to AWS, not the direction of the application’s business transaction.

Office → corporate DNS → inbound endpoint → AWS private zone
AWS app → VPC resolver → outbound endpoint → corporate DNS

The first lookup finds the order application. The second finds ERP. Neither lookup itself opens an application connection.

Essential mechanics

Associate the cloud.example.com private hosted zone with the inbound endpoint’s VPC. Configure corporate DNS to forward that suffix to the inbound endpoint IPs, not to the VPC’s Amazon-provided resolver address.

Create an outbound rule for corp.example.com, targeting the corporate DNS servers, and associate it with the application VPC. Applications continue using the normal VPC resolver; the matching rule sends only corporate queries outward. AWS RAM can share that rule with other accounts, but rule sharing does not automatically associate private hosted zones.

Place endpoint IPs in multiple AZs and use redundant corporate DNS servers. Allow UDP and TCP 53, with appropriate security groups and routes in both directions. TCP matters for responses that cannot complete over UDP.

Avoid broad forwarding rules that send the same query back and forth. A matching private zone with a missing record can return NXDOMAIN instead of falling back to public DNS; overlapping namespaces require deliberate ownership.

Validation and when the answer changes

  • Resolve each service from its actual clients using normal DNS settings, including a TCP query.
  • Test a nonexistent name, one unavailable DNS target, and inspect query logs for loops or incorrect suffix matching.
  • After resolution succeeds, separately test the application port and authentication.

Custom DNS behavior unsupported by Resolver could justify EC2 forwarders. If applications no longer depend on corporate services, remove unnecessary forwarding rather than preserving it indefinitely.

Remember and AWS docs

  • Network reachability does not automatically provide DNS visibility.
  • Inbound endpoints let external networks query AWS Resolver.
  • Outbound rules send selected VPC queries to external DNS servers.
  • Private-zone association and forwarding-rule association are separate.
  • A successful DNS lookup does not prove the service is reachable or healthy.

N05Exam tasks: 1.1, 2.3, 2.6

Letting private batch workers read S3 and Secrets Manager without internet egress

Situation and requirements

You design an insurer’s document-processing pipeline. Private EC2 workers read several terabytes nightly from S3 and retrieve a database credential from Secrets Manager. Everything is in one Region, and workers use prebuilt images rather than downloading packages at runtime.

Security prohibits general internet egress and permits only the approved bucket prefix and secret. Finance wants to avoid routing bulk S3 traffic through a NAT gateway. Removing public IPs alone would not meet either requirement.

This is a fictional exercise; data volume is an assumption.

Options and decision

Option Mechanism Fit here
NAT gateway Outbound access to public service endpoints Adds processing charges and a general egress path unless separately restricted.
Interface endpoints for both services Private ENIs for service access Works, but incurs S3 endpoint charges that these same-VPC workers can avoid.
S3 gateway endpoint plus Secrets Manager interface endpoint Route-based S3 access and private secret access Meets the connectivity requirement with a lower-cost S3 path.

Choose the mixed endpoint design, then restrict resource permissions separately. Connectivity to an AWS service does not mean permission to use every resource in it.

Mental model and flow

A gateway endpoint changes routing; an interface endpoint supplies private network interfaces.

Worker → S3 prefix-list route → gateway endpoint → approved bucket
Worker → private DNS → interface endpoint ENI → Secrets Manager

Both use normal SDK service names. The client does not need special endpoint IPs in application code.

Essential mechanics

Associate the S3 gateway endpoint with every worker subnet’s route table. It uses an AWS-managed prefix list of S3 address ranges and has no endpoint security group. S3 DNS can still return public-looking addresses even though the route does not use the internet. Gateway endpoints have no endpoint hourly or processing charge; ordinary S3 charges remain.

For Secrets Manager, create endpoint ENIs across the worker AZs, enable private DNS and VPC DNS support, and allow TCP 443 from the worker security group. Interface endpoint hourly and data charges apply; multiple AZs do not guarantee every connection is AZ-local.

The instance role permits only the required object reads, secret retrieval, and KMS decryption. Endpoint policies restrict requests; they do not independently grant IAM permissions. A bucket restriction using aws:SourceVpce must account for administration and recovery paths to avoid locking them out.

S3 or Secrets Manager using KMS on the application’s behalf does not itself require a worker-side KMS endpoint. Direct KMS API calls would. Inventory other runtime dependencies, including logging, before removing internet routes.

Validation and when the answer changes

  • Run the job from both AZs with no default internet route.
  • Verify the intended reads succeed and another prefix or secret is denied.
  • Confirm logs, operational access, and decryption still work; inspect DNS and routes separately.

On-premises clients cannot directly use this VPC’s S3 gateway endpoint over VPN or DX. For that requirement, evaluate an S3 interface endpoint and hybrid DNS rather than reusing this design unchanged.

Remember and AWS docs

  • Private subnets can still have internet egress through NAT.
  • Gateway and interface endpoints use different routing/security models.
  • Endpoint access and resource authorization are separate checks.
  • A public-looking DNS answer does not establish the packet’s route.
  • No NAT does not mean no service charges or runtime dependencies.

Diagnosing database timeouts after adding an EKS node subnet

Situation and requirements

You are the on-call engineer for an EKS application using private RDS PostgreSQL. After adding a node subnet, pods on new nodes time out opening database connections; pods on old nodes work. Both run the same image and credentials.

The cluster uses VPC CNI pod addresses, without security groups for pods. Both node groups share a security group, and RDS is in the same VPC. You need a targeted repair, not a public database or temporarily unrestricted network.

All observations and the root cause below are fictional exercise inputs.

Options and decision

Approach What it reveals Fit here
Open every network rule Whether removing controls changes the symptom Increases exposure and obscures which rule mattered.
Capture packets everywhere Actual traffic at capture points Useful later, but unnecessarily broad before identifying the failed stage.
Compare a working and failing path Differences in DNS, interfaces, routes, and controls Best starting point for a subnet-correlated failure.

Compare first, then fix the proven mismatch. Record pod IPs, subnets, database DNS answers, and whether the error occurs during DNS, TCP, TLS, authentication, or SQL execution.

Mental model and flow

The response needs a permitted path too. For one sample connection:

Request: pod:40000 → RDS:5432
Response: RDS:5432 → pod:40000

Port 40000 is the client’s temporary, or ephemeral, port. The response’s destination is not the database listening port.

Essential mechanics

Security groups are stateful: permitted connections allow their response traffic. Network ACLs are stateless: rules must allow each direction separately.

In this exercise, both pods resolve the same RDS address. The failing pod times out before authentication. Routes and security groups match the working path, but flow logs show rejected return traffic. Comparing ACLs reveals that the new subnet lacks the inbound ephemeral-port allowance present on the old subnet.

Repair that ACL through infrastructure as code. Allow the actual client ephemeral range from the database subnet ranges, checking rule order. Do not allow only the sample port 40000; subsequent connections can use other ports. Inspect both subnet boundaries, not only the source ACL.

A flow-log REJECT alone does not name the responsible rule. Reachability Analyzer can inspect supported AWS network paths using the ENI carrying the pod address, but it does not send packets, check database health, or evaluate every Kubernetes policy.

Validation and when the answer changes

  • Repeat connection and query checks from old and new nodes under representative traffic.
  • Confirm connection errors fall while unrelated inbound access stays blocked.
  • Correct the subnet template so the next deployment does not recreate the omission.

If the TCP connection succeeds but SQL is slow, investigate queries and database capacity instead. An ACCEPT record also does not prove end-to-end success: TLS, network policies, and connection pools may still fail.

Remember and AWS docs

  • Identify the failed connection stage before changing infrastructure.
  • With VPC CNI, pod traffic is not necessarily sourced from the node’s primary IP.
  • Stateful security groups and stateless ACLs handle responses differently.
  • Flow logs and configuration analysis complement, not replace, application evidence.
  • Intermittent EKS failures do not automatically mean an ACL problem.

Improving a Singapore-hosted storefront for European shoppers without moving customer records

Situation and requirements

You support a Singapore retailer expanding into Europe. European product pages load slowly even though origin processing is healthy. Public images, scripts, and catalog responses account for about 80% of delivered bytes; checkout remains personalized and writes to Singapore.

Security permits global caching of public content, but has not approved global edge processing for authenticated APIs. The product team accepts a catalog up to one minute stale, provided checkout rechecks price and stock. You must improve browsing without promising local-speed checkout or starting a multi-Region database project.

This is a fictional exercise; traffic observations are supplied assumptions.

Options and decision

Option Mechanism Fit here
More Singapore instances Add compute capacity Does not address long-distance downloads when origin compute is healthy.
Global Accelerator Route supported TCP/UDP traffic through AWS’s network using static anycast addresses Can improve network paths, but does not cache the reusable content.
CloudFront Serve public cache hits from nearby edge locations Best fit for the dominant traffic; regional writes still travel to Singapore.

Put public assets and catalog responses behind CloudFront. Keep authenticated operations on the existing regional API for this phase.

Mental model and flow

A CDN moves reusable responses closer to readers, not the authoritative database closer to writers.

Image → CloudFront cache → S3 only on a miss
Public catalog → CloudFront cache → Singapore ALB only on a miss
Checkout → Singapore API → Singapore database

Route 53 latency routing alone would not help: it chooses among existing deployments, not create a closer one.

Essential mechanics

Use long lifetimes for versioned assets. For catalog responses, configure both edge and browser caching within the one-minute allowance and avoid stale-serving settings that exceed it. The cache key must include supported representation differences, such as currency and language.

Only a genuinely public handler belongs behind that catalog behavior. A response containing account discounts must not enter a shared cache without a deliberate isolation design. Here, keep personalized responses out entirely. Configure the browser’s regional API integration, including narrowly scoped CORS where needed.
