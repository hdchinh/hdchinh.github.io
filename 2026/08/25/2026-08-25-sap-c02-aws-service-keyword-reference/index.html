SAP-C02 AWS Service Keyword Reference

Executive summary

For SAP-C02, trying to memorize the entire AWS catalog is the wrong abstraction. AWS’s current exam guide says the certification evaluates the ability to design optimized solutions across organizational complexity, new solutions, continuous improvement, and migration/modernization. The current weighting is 26%, 29%, 25%, and 20% respectively. AWS also explicitly says its in-scope service list is non-exhaustive and subject to change. citeturn1view1turn1view0

For a mechanism-first learner, the useful first pass is therefore not “learn every feature.” It is:

Know what architectural job each service owns, the mechanism that makes it different, and the constraint that causes you to choose it over its nearest alternative.

The Well-Architected Framework reinforces exactly this mode of thinking: architectural decisions are trade-offs across operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability. citeturn0search5turn0search1

The roughly sixty names below are the first-pass vocabulary I would want in your head before deep study. This priority ordering is my exam-focused synthesis, not an official AWS weighting. AWS itself does not assign relative importance to individual services in its in-scope list. citeturn1view0

The mental map to retain is:

Identity → who can do what?

Compute → who manages the runtime?

Storage → object, block, or file?

Database → what access pattern and consistency model?

Networking → how should traffic move?

Security → prevent, detect, or aggregate/respond?

Observability → metric, API action, configuration, or request trace?

Integration → queue, fan-out, route, or orchestrate?

Governance → how do we control many accounts consistently?

Cost → observe, alert, right-size, or commit?

Migration → what is moving, with what downtime and bandwidth?

Data/ML → ad hoc query, ETL, warehouse, stream, Kafka, or custom ML?

These are the categories and service names worth recognizing immediately before you start drilling individual topics. They are drawn primarily from AWS’s current SAP-C02 in-scope list, with prioritization based on the tasks explicitly called out in the four exam domains. citeturn1view2turn1view3turn1view4turn5view0

Core infrastructure

Identity

AWS explicitly expects SAP-C02 candidates to understand IAM, IAM Identity Center, cross-account access, third-party identity integration, multi-account environments, and centralized governance. AWS’s identity decision guide separates workforce identity, application identity, AWS authorization, and directory integration rather than treating “IAM” as one monolithic subject. citeturn1view2turn6search0

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
IAM Authorize AWS principals against AWS resources Effective access comes from intersecting/combining policy layers; explicit deny wins. Roles beat long-lived user credentials for workloads. “Give workload/account X least-privilege access to Y”; cross-account roles; permission boundaries; resource vs identity policies.
IAM Identity Center Central workforce access to AWS accounts/apps Federation + permission sets across accounts; designed for human workforce, not application customers. Enterprise has AD/IdP and 100 AWS accounts; replace per-account IAM users.
STS Issue temporary AWS credentials Role assumption/federation produces limited-lifetime credentials instead of durable keys. Cross-account access, federated users, temporary workload credentials.
Cognito Identity for application end users User pools authenticate users; identity pools can exchange identities for temporary AWS credentials. Mobile/web customers sign in; users need controlled access to S3/DynamoDB/API.
Directory Service Connect/manage Microsoft-directory-style identity workloads Choose when AD semantics/integration are the requirement rather than simply AWS account SSO. Windows workloads, domain join, existing Microsoft AD integration.
RAM Share supported AWS resources across accounts Share one resource rather than duplicate it or create broader network connectivity. Shared subnets, Transit Gateway, and other centrally owned resources across an Organization.

The exam decision tree is principal → credential type → authorization boundary → account scope. First ask whether this is workforce, workload, customer, or Microsoft-directory identity. Then ask whether the control belongs inside an IAM policy, at the account/OU guardrail level, or on the resource itself. Temporary credentials are the default architectural instinct; AWS documents STS credentials as the basis for roles and federation. citeturn6search2turn3search3turn6search4turn6search9

Compute

AWS’s compute guidance distinguishes serverless functions, containers, and virtual machines primarily by control and operational responsibility. The SAP-C02 migration domain explicitly expects candidates to choose among EC2, ECS, EKS, Fargate and related platforms when rearchitecting workloads. citeturn2search6turn2search14turn1view3

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
EC2 General-purpose VM compute Maximum OS/runtime/network/storage control; you inherit the most host-level operations. Legacy software, custom OS/kernel/network requirements, licensing, specialized instances.
EC2 Auto Scaling Match EC2 capacity to load and replace unhealthy instances Converts a fleet from static hosts into an elastic pool; economics depend on scaling policy and purchase model. Variable demand, automatic replacement, HA across AZs.
Lambda Event-driven function execution Removes server management and scales by invocation/concurrency; constrained execution model makes it unsuitable for every workload. Bursty events, asynchronous processing, serverless APIs, glue logic.
ECS AWS-native container orchestration Container abstraction without requiring the Kubernetes API/ecosystem. “Run containers with minimum operational complexity” when Kubernetes is not required.
EKS Managed Kubernetes control plane Gives Kubernetes compatibility/ecosystem at the cost of retaining Kubernetes complexity. Existing Kubernetes platform/tooling, portability requirement, Kubernetes APIs/operators.
Fargate Run ECS/EKS tasks without managing worker nodes Trades host-level control and fleet/bin-packing management for managed compute capacity. “Containers, but company does not want to manage EC2 worker nodes.”

The key distinction is not EC2 vs Lambda vs containers as products; it is how much control requires how much operational responsibility. AWS Well-Architected guidance explicitly contrasts Fargate’s serverless container model with EC2 when installation/configuration/control of the compute environment is required. citeturn2search38turn2search2

Storage

AWS’s storage decision guide starts with the storage interface itself: object, block, or file, then moves into performance, sharing, availability, migration compatibility, and cost. SAP-C02 explicitly calls out S3, EBS, EFS, FSx and Storage Gateway when selecting architectures for migrated workloads. citeturn2search1turn1view3

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
S3 Durable scalable object storage Object semantics, not a traditional block/POSIX filesystem; lifecycle/storage classes separate access frequency from retention economics. Data lake, static assets, backup targets, archives, cross-Region data protection.
EBS Persistent block storage for compute Block device semantics and high-performance storage close to EC2; volume availability is AZ-oriented, snapshots provide separate protection. Database/filesystem requiring block storage and predictable I/O.
EFS Managed shared Linux/NFS filesystem Multiple compute instances can mount the same elastic file namespace; convenience/shared access vs block-storage economics/performance. Shared Linux files across EC2/ECS/Lambda and multiple AZs.
FSx Managed specialized filesystems Preserve specific filesystem/protocol behavior such as Windows, Lustre, ONTAP or OpenZFS. SMB/Windows lift-and-shift, NetApp dependency, HPC/Lustre workloads.
AWS Backup Centralize backup policy and retention Separates backup governance from service-by-service scripts; backup/restore is not the same mechanism as active HA. Cross-account backup policies, retention/compliance, centralized protection.
Storage Gateway Bridge on-premises applications to AWS storage Keeps familiar NFS/SMB/iSCSI-style interfaces on-prem while AWS becomes the durable backend/tier. Hybrid storage, staged migration, cloud-backed backup/archive without rewriting apps.

For storage questions, ask in this order: what interface does the application require → can multiple hosts share it → latency/IOPS → AZ/Region failure requirement → retention/access frequency → migration compatibility. “Shared filesystem” should immediately move you away from EBS; “existing SMB/NetApp/Lustre semantics” should move you toward FSx; “object/archive/data lake” toward S3. citeturn2search1turn2search5turn2search21

Database

AWS’s database decision guide frames selection around workload model rather than “which database is fastest.” The exam’s migration and modernization domain explicitly expects candidates to choose among RDS, DynamoDB, OpenSearch, self-managed EC2 databases, Aurora Serverless, ElastiCache and other purpose-built stores. citeturn2search0turn1view3

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
RDS Managed conventional relational databases AWS manages infrastructure chores while preserving familiar engines; Multi-AZ solves HA, read replicas primarily solve read scaling. Lift/replatform Oracle/SQL Server/MySQL/PostgreSQL-compatible workloads while retaining relational semantics.
Aurora AWS-optimized MySQL/PostgreSQL-compatible relational database Cloud-native managed storage/replica architecture gives stronger scaling/HA options than a conventional single DB host model. High-throughput relational workload, many readers, cross-Region relational DR/global design.
DynamoDB Serverless key-value/document database Scale comes from designing around known partition-key/access patterns rather than arbitrary relational joins. Huge request volume, predictable key-based access, low operational overhead.
ElastiCache In-memory cache/data layer Trades durability/authoritative state semantics for extremely fast access; introduces cache consistency/invalidation questions. Remove read pressure from RDS, sessions, hot data, low-latency repeated reads.
DocumentDB Managed document database with MongoDB compatibility Choose for document/Mongo-compatible workloads rather than forcing document access patterns into relational schemas. Migrate/manage a Mongo-style application without self-managing database hosts.
Neptune Purpose-built graph database Optimizes relationship traversal instead of repeated multi-table joins. Social graphs, knowledge graphs, fraud/relationship traversal.

The most important database habit is to identify the access pattern before the service. Relational transactions and joins point toward RDS/Aurora; predictable key lookup and enormous horizontal scale toward DynamoDB; repeated hot reads may justify ElastiCache; graph traversal toward Neptune. Then overlay RTO/RPO, regional topology, migration compatibility and operations. AWS’s DR guidance explicitly maps database choice and architecture to RTO/RPO requirements. citeturn2search16turn2search0

Connectivity and runtime control

Networking

SAP-C02 Domain One explicitly tests multi-VPC connectivity, hybrid connectivity, DNS, network segmentation, Regions/AZ selection, troubleshooting traffic flows, and service endpoints. AWS’s networking decision guide covers these as different connectivity jobs rather than interchangeable network products. citeturn1view2turn3search1

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
VPC Isolated AWS network boundary Subnets/routes determine paths; security groups are stateful workload controls while NACLs operate at subnet boundaries. CIDR design, segmentation, private/public tiers, VPC endpoints, overlapping networks.
ELB Distribute traffic across application targets ALB reasons at HTTP/L7; NLB targets lower-level TCP/UDP/L4 requirements. HTTP routing/host/path vs very high-performance TCP/UDP/static-IP-type requirements.
Route 53 DNS and DNS-based traffic steering Changes name resolution rather than becoming the packet/data path itself. Failover, weighted/latency/geolocation DNS, private hosted zones, hybrid DNS/Resolver.
Transit Gateway Hub for many VPC/on-prem network attachments Replaces many point-to-point relationships with transitive hub-and-spoke routing; adds centralized routing and processing economics. Dozens/hundreds of VPCs, multiple accounts, centralized hybrid network.
Direct Connect Dedicated private network connectivity to AWS Provides a private, more predictable hybrid path; resilience and encryption are separate architectural decisions. Sustained hybrid bandwidth, predictable connectivity, large enterprise data center integration.
CloudFront Edge CDN for web/content delivery Edge caching reduces origin traffic/latency; this is different from simply accelerating arbitrary TCP/UDP traffic. Global HTTP content, caching, S3 origins, edge security.

Networking questions usually reduce to scope and path: inside one VPC, VPC-to-VPC, many VPCs, service-to-service private access, on-prem-to-AWS, or users-to-global-application. For a large multi-account topology, Transit Gateway is the central hub pattern AWS documents; for global edge traffic remember that CloudFront is fundamentally content/CDN-oriented, while Global Accelerator is the second-pass service to inspect when the requirement is global TCP/UDP acceleration through AWS’s network rather than content caching. PrivateLink is likewise worth a second pass for privately exposing a service without creating broad network connectivity. citeturn0search13turn3search4turn3search25

Security

The SAP-C02 guide explicitly expects encryption strategy, certificate/key management, centralized security events, least privilege, vulnerability detection, automated response and multi-account security controls. AWS’s security decision guidance separates preventive, detective and governance functions. citeturn1view2turn1view4turn3search5

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
KMS Managed cryptographic key control Data services commonly integrate with KMS so key policy/control is separate from storage itself; think envelope-encryption architecture and key ownership. Customer-controlled encryption at rest, cross-account encryption, key rotation/control.
Secrets Manager Securely store and rotate application secrets Secret lifecycle/rotation rather than embedding static credentials in config/code. RDS credentials, automatic secret rotation, application secrets.
GuardDuty Managed threat detection Consumes AWS security/activity signals and produces findings; detects, it is not your inline blocking firewall. Suspicious credentials, anomalous API/network/S3/EKS behavior.
Inspector Find workload/package vulnerabilities and exposure Vulnerability assessment is a different mechanism from behavioral threat detection. CVEs/vulnerability scanning for EC2/container/Lambda-type workloads.
Security Hub Centralize and prioritize security posture/findings Aggregates/correlates security signals; it does not replace the detector producing the signal. Central security account across many accounts/Regions, consolidated findings/compliance posture.
WAF / Shield Protect internet-facing applications from malicious web requests / DDoS WAF = application-request rules; Shield = DDoS protection. SQL injection/rate/IP rules → WAF; DDoS-specific requirement → Shield.

The exam-level distinction is prevent vs detect vs aggregate vs remediate. GuardDuty detects suspicious behavior; Inspector looks for vulnerabilities; Security Hub centralizes and prioritizes findings; WAF filters application requests. AWS’s Security Reference Architecture specifically treats GuardDuty, Inspector, Macie and Security Hub as complementary building blocks rather than competing products. citeturn3search17turn3search26turn3search29

Observability

The current exam guide directly calls out CloudWatch for monitoring/logging and AWS Config for configuration compliance; CloudTrail appears in centralized auditing/security requirements, while X-Ray remains in the official in-scope list. citeturn1view4turn5view0

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
CloudWatch Operational telemetry: metrics, logs, alarms Measures what the system is doing and can trigger alarms/actions; supports centralized cross-account observability. CPU/latency/errors, log monitoring, alarms, dashboards, automatic remediation triggers.
CloudTrail Audit AWS account/API activity Records who/what called AWS APIs rather than application performance metrics. “Who deleted/changed this resource?”, governance, security audit, compliance.
Config Track resource configuration and evaluate compliance Reasons about what configuration exists/changed, not who made the API call. “Ensure every bucket has setting X”; detect configuration drift/noncompliance.
X-Ray Distributed request tracing Propagates trace context across request paths to expose downstream latency/errors. Microservices request takes 4 seconds; determine which dependency causes it.

A very high-value exam distinction is: CloudWatch = behavior, CloudTrail = activity/audit, Config = resource state/compliance, X-Ray = request path. AWS publishes a dedicated CloudTrail-versus-CloudWatch decision guide, while Config continuously evaluates supported resource configurations and X-Ray builds traces/service graphs across downstream dependencies. citeturn8search0turn8search25turn8search3

Application Integration

The modernization domain explicitly names SQS, SNS, EventBridge and Step Functions and expects candidates to recognize opportunities to decouple application components and choose the appropriate integration service. AWS additionally publishes a specific decision guide comparing SQS, SNS and EventBridge. citeturn1view3turn2search7

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
SQS Durable asynchronous work queue Consumer pulls work; queue absorbs bursts/backpressure. Standard favors scale with at-least-once delivery; FIFO adds ordering/deduplication constraints. Producer and consumer scale differently; jobs cannot be lost; retry/DLQ pattern.
SNS Push pub/sub fan-out One publication can push to many subscribers; pair with SQS when each subscriber needs durable independent buffering. Same event must reach email, Lambda and multiple processing queues.
EventBridge Route events by event content/source Event bus decouples producers from destinations and performs rule-based routing. AWS/SaaS/domain events, cross-account event routing, content-based routing.
Step Functions Explicit workflow orchestration Persists workflow state and coordinates branches/retries/timeouts rather than relying on implicit service choreography. Multi-step business process, retries, parallel work, approval/orchestration.
Amazon MQ Managed traditional message broker Preserve ActiveMQ/RabbitMQ protocols/semantics; migration compatibility can outweigh cloud-native simplicity. Existing JMS/AMQP/broker-dependent application with minimal rewrite requirement.
API Gateway Managed front door for APIs Separates API ingress concerns such as authentication/throttling/routing from compute behind it. Public/serverless API, Lambda backend, throttling/auth requirement without managing proxies.

Mechanistically: SQS holds work, SNS broadcasts, EventBridge routes events, Step Functions owns workflow state. Amazon MQ enters when legacy protocol compatibility is the constraint, while API Gateway is ingress rather than internal asynchronous decoupling. That distinction is more valuable for SAP-C02 than memorizing individual service limits. citeturn2search3turn2search19

Enterprise operating model

Management & Governance

Multi-account architecture is a first-class SAP-C02 concern. Domain One explicitly requires Organizations, Control Tower, account structure, centralized logging and a multi-account governance model. AWS’s current governance guidance distinguishes organization-wide guardrails, landing-zone governance, infrastructure deployment, fleet operations and approved self-service. citeturn1view2turn7search20

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
Organizations Create/group/govern many AWS accounts OUs define administrative structure; SCPs set permission ceilings but do not grant permissions. Block a Region/service for every account in an OU; consolidated multi-account governance/billing.
Control Tower Establish/govern a multi-account landing zone Opinionated orchestration over services such as Organizations and IAM Identity Center; trades customization freedom for faster standardized governance. Company wants a secure multi-account baseline, Account Factory and centralized controls.
CloudFormation Declarative AWS infrastructure as code Infrastructure becomes desired-state templates; StackSets extend deployment across accounts and Regions. Deploy identical baseline/resources to 50 accounts × multiple Regions.
Systems Manager Operate fleets centrally Performs management/automation/patching without treating every server as a manually administered snowflake. Patch servers, execute runbooks, manage AWS/on-prem nodes at scale.
Service Catalog Offer approved infrastructure/products for self-service Platform team publishes constrained products; developers consume them without unrestricted infrastructure permissions. Teams may provision resources, but only corporate-approved templates/configurations.

A useful hierarchy is Organizations = account hierarchy/guardrails; Control Tower = governed landing-zone operating model; CloudFormation = resource deployment; Service Catalog = constrained self-service; Systems Manager = ongoing fleet operations. CloudFormation StackSets can push a common template across accounts and Regions, while Control Tower builds a governed multi-account environment on top of Organizations and related services. citeturn7search1turn7search4turn7search8turn7search14

Cost & Billing

Cost optimization appears explicitly in both Domain One and Domain Three. AWS expects candidates to know monitoring, tagging, purchase models, right-sizing, networking/data-transfer cost, alerts/reporting, Cost Explorer, Budgets, Cost and Usage Reports, Compute Optimizer and Savings Plans. citeturn1view2turn1view4

Service/tool Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
Cost Explorer Interactive cost/usage analysis Good for exploring trends, filtering/grouping and commitment recommendations; not the rawest billing dataset. “Which service/account drove the increase?”
Cost and Usage Report — CUR Granular billing/usage dataset Line-item data supports deep allocation/analysis pipelines; more flexible but less immediately interactive than Cost Explorer. Detailed chargeback, SQL/BI analysis, enterprise FinOps.
AWS Budgets Threshold-based cost/usage monitoring and actions Compares actual/forecast usage against defined budget conditions. Alert/take action when team/account spend crosses threshold.
Compute Optimizer Right-sizing recommendations Uses observed utilization to recommend resource sizing rather than changing purchase commitment. Underutilized EC2/Fargate/etc.; reduce waste without architecture rewrite.
Savings Plans Reduce eligible compute price through usage commitment Exchange commitment for discount; flexibility varies by plan type, but commitment risk remains. Stable baseline compute spend where On-Demand flexibility is unnecessary.
Pricing Calculator Estimate architecture cost before deployment Forward estimate rather than historical spend analysis. Compare proposed architectures or create migration TCO estimate.

The exam often separates usage optimization from price optimization. Right-sizing/scaling/Spot address consumption; Savings Plans or RIs address price model; Cost Explorer/CUR provide visibility; Budgets provide control signals. Also treat network topology as a cost decision: SAP-C02 explicitly includes data-transfer cost, so architectures involving NAT, cross-AZ/Region traffic and centralized networking should never be evaluated on compute price alone. citeturn4search4turn4search16turn4search1turn1view4

Migration & Modernization

Migration is 20% of scored SAP-C02 content. AWS explicitly tests portfolio assessment, the 7Rs, TCO, data transfer, server migration, database migration, networking/DNS, identity, governance, target compute/storage/database selection and modernization through serverless, containers and decoupling. citeturn1view1turn1view3

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
Migration Hub Coordinate/track migration portfolio Management/visibility layer rather than the data-transfer mechanism itself. Many applications/waves/tools need centralized migration status.
Application Migration Service / AWS Transform MGN Rehost servers into AWS Continuous block-level replication prepares source servers for low-downtime cutover. “Move hundreds of VMware/physical servers to EC2 with minimal app changes.”
DMS Move/replicate database data Full load plus CDC can minimize downtime; heterogeneous engines additionally create schema/code-conversion concerns. Database stays online while migration occurs; source/target databases differ.
DataSync Online bulk file/object data movement Initial bulk copy followed by incremental transfers supports cutover over available network connectivity. NAS/NFS/SMB/object data to S3/EFS/FSx with network available.
Snow Family Physical/offline data movement and edge workloads Move the medium rather than push all bytes over the WAN when network transfer is impractical. Massive dataset / constrained connectivity.
Transfer Family Managed SFTP/FTPS/FTP-style transfer into AWS storage Preserves familiar partner/file-transfer interfaces while removing self-managed transfer servers. External business partners require SFTP but target data should land in AWS-managed storage.

A migration question should trigger four questions: what moves (server/database/files) → rehost/replatform/refactor? → allowable downtime/RPO → available bandwidth/time? MGN is server/block replication; DMS is database migration/CDC; DataSync is online file/object movement; Snow represents offline physical transfer. Current AWS documentation is worth noting here: the SAP-C02 in-scope list still includes Snow Family, while current Snowball Edge documentation says Snowball Edge is no longer available to new customers. For the exam, learn the offline-transfer architectural pattern because AWS still lists Snow Family in scope, rather than memorizing current procurement details. citeturn9search4turn9search5turn9search2turn5view0turn9search26

There is another terminology transition worth knowing: current AWS documentation now uses AWS Transform MGN for MGN, while the current SAP-C02 scope page still lists AWS Application Migration Service. Likewise, current DMS supports DMS Schema Conversion, although AWS SCT remains named in the exam’s current in-scope list. Recognizing both names prevents documentation changes from becoming exam confusion. citeturn9search4turn9search1turn5view0

Data and ML

AWS lists a broad set of analytics and ML products as SAP-C02 in-scope, but the architecturally important first pass is to distinguish query, integration/ETL, warehouse, streaming, Kafka compatibility, and custom ML. AWS’s analytics decision guide uses similar workload-oriented separation. citeturn5view0turn4search2

Service Primary job Mechanism / trade-off to remember Typical SAP-C02 hook
Athena Serverless SQL queries over data, especially S3 Query data in place rather than loading a warehouse first; economics depend heavily on how much data queries scan. Ad-hoc SQL over S3 logs/data lake with minimal infrastructure.
Glue Serverless data integration/catalog/ETL Discovers/catalogs schemas and transforms data between systems; complements query engines rather than replacing the storage layer. Build ETL/data catalog around S3/Athena/Redshift; schema discovery.
Redshift Analytical data warehouse Optimized for repeated analytical/BI workloads rather than transactional OLTP or occasional raw-S3 queries. Enterprise warehouse, complex repeated analytical queries, BI.
Kinesis Data Streams AWS-native real-time event stream Producers write ordered stream records that consumers process independently; choose when the application owns stream-processing behavior. Clickstream/telemetry/events processed continuously by several AWS consumers.
MSK Managed Apache Kafka Keep Kafka APIs/ecosystem and operational semantics; compatibility is the reason to accept more Kafka-specific complexity. Existing Kafka producers/consumers, Kafka ecosystem, migration without rewriting clients.
SageMaker AI Build/train/deploy custom ML models Appropriate when you need an ML lifecycle/model of your own, rather than a simple prebuilt AI API. Custom training/inference pipeline, model deployment and ML platform requirement.

The useful exam distinction is: Athena = query data where it sits; Glue = catalog/transform it; Redshift = warehouse it; Kinesis = AWS-native stream; MSK = Kafka stream. SageMaker AI is the broad custom-ML platform. OpenSearch should be your immediate second-pass keyword for search/log analytics, while services such as Comprehend, Rekognition, Textract, Transcribe and Translate are purpose-built ML APIs that usually become easy to select once the business requirement explicitly names their modality. AWS’s current scope page includes all of these. citeturn4search5turn4search26turn4search20turn4search29turn5view0

One current exam nuance: the official SAP-C02 guide now lists generative-AI security/responsible-AI topics such as Amazon Bedrock Guardrails as emerging topics, but AWS states those emerging-topic questions can appear as unscored pretest questions. Therefore, Bedrock deserves recognition but should not displace the scored architecture fundamentals above in your first-pass study map. citeturn1view1

The fastest daily review is therefore not sixty independent flashcards. Compress the whole map into twelve architectural oppositions:

IAM vs Identity Center vs Cognito → AWS authorization / workforce / customers

EC2 vs Lambda vs Fargate → host control / functions / managed containers

S3 vs EBS vs EFS → object / block / shared file

RDS-Aurora vs DynamoDB → relational model / access-pattern model

Route 53 vs CloudFront vs Transit Gateway → DNS / edge delivery / network hub

GuardDuty vs Inspector vs Security Hub → threat / vulnerability / aggregation

CloudWatch vs CloudTrail vs Config vs X-Ray → behavior / audit / state / trace

SQS vs SNS vs EventBridge vs Step Functions → queue / fan-out / route / workflow

Organizations vs Control Tower vs CloudFormation → guardrails / landing zone / resources

Compute Optimizer vs Savings Plans → consume less / pay less per unit

MGN vs DMS vs DataSync → servers / databases / files

Athena vs Redshift vs Kinesis/MSK → ad hoc / warehouse / stream

That is the overview layer worth having before opening IAM, RDS, VPC, S3, or another topic with the tutor. It gives you enough vocabulary to recognize what architectural mechanism a SAP-C02 scenario is actually testing, without prematurely memorizing service trivia. citeturn0search5turn1view1
